This page describes how Prophecy generates, stores, and shares audit logs for Prophecy deployments.

Setting up audit logs requires collaboration with Prophecy. [Contact Prophecy](/administration/getting-help/get-in-touch) to:

- Export audit logs on demand.
- Configure automatic syncing to your own storage.
- Set a custom retention period for stored logs.

## Storage location

Prophecy stores audit logs in the same cloud platform as your deployment:

- For AWS deployments, audit logs are stored in Amazon S3.
- For Azure deployments, audit logs are stored in Azure Blob Storage.
- For Google Cloud Platform deployments, audit logs are stored in Google Cloud Storage.

## Event types

When audit logs are enabled for your Prophecy deployment, they capture the following information:

- Actions in the control plane, such as sign-ins, user and team changes, project saves and publishes, and changes to credentials and security settings.
- Actions on the execution plane, such as fabric, connection, deployment, pipeline run, schedule, and DataBox operations.

Each event has a fixed event type and a category. The following sections list the events that Prophecy logs.

## Control plane events

Control plane events record actions in the Prophecy control plane, such as the Prophecy UI and its services.

### Authentication

| Event type           | Category | Description |
| -------------------- | ------ | ----------- |
| `LOGIN_FEDERATED`    | `AUTH` | A user signed in through a federated identity provider (OAuth, OIDC, or SAML) |
| `LOGIN_LDAP`         | `AUTH` | A user signed in through LDAP |
| `LOGIN_BUILTIN`      | `AUTH` | A user signed in with a Prophecy username and password |
| `LOGOUT`             | `AUTH` | A user signed out |
| `SESSION_REVOKE_ALL` | `AUTH` | An admin ended all of another user's sessions |

### Users and teams

| Event type           | Category   | Description |
| -------------------- | ---------- | ----------- |
| `USER_CREATE`        | `IDENTITY` | A user was created |
| `USER_DELETE`        | `IDENTITY` | A user was deleted |
| `USER_DEACTIVATE`    | `IDENTITY` | An admin deactivated a user. The user's sessions end at the same time |
| `USER_REACTIVATE`    | `IDENTITY` | An admin reactivated a user |
| `USER_IMPERSONATE`   | `IDENTITY` | A privileged user, such as a Support user, requested access to act as another user |
| `PASSWORD_CHANGE`    | `IDENTITY` | An admin set a user's password |
| `TEAM_CREATE`        | `IDENTITY` | A team was created |
| `TEAM_DELETE`        | `IDENTITY` | A team was deleted |
| `TEAM_MEMBER_ADD`    | `IDENTITY` | A user was added to a team |
| `TEAM_MEMBER_REMOVE` | `IDENTITY` | A user was removed from a team |
| `ROLE_CHANGE`        | `IDENTITY` | A team member's role changed, for example when a member was made a team admin |

### Fabrics and projects

| Event type        | Category    | Description |
| ----------------- | ----------- | ----------- |
| `FABRIC_CREATE`   | `DATA_FLOW` | A fabric was created |
| `FABRIC_DELETE`   | `DATA_FLOW` | A fabric was deleted |
| `PROJECT_CREATE`  | `COMPUTE`   | A project was created |
| `PROJECT_DELETE`  | `COMPUTE`   | A project was deleted |
| `PROJECT_SAVE`    | `COMPUTE`   | Changes to a project were saved (committed) |
| `PROJECT_PUBLISH` | `COMPUTE`   | A project version was published |

### Pipeline activity

| Event type      | Category   | Description |
| --------------- | ---------- | ----------- |
| `PIPELINE_OPEN` | `ACTIVITY` | A user opened a pipeline in the editor |
| `PIPELINE_EDIT` | `ACTIVITY` | A user edited a pipeline. Recorded once per editing session |

### Credentials and security settings

| Event type                 | Category         | Description |
| -------------------------- | ---------------- | ----------- |
| `ACCESS_TOKEN_CREATE`      | `SECRETS`        | A personal access token was created |
| `ACCESS_TOKEN_DELETE`      | `SECRETS`        | A personal access token was deleted |
| `GIT_CREDENTIAL_ADD`       | `SECRETS`        | Git credentials were added |
| `GIT_CREDENTIAL_UPDATE`    | `SECRETS`        | Git credentials were updated |
| `GIT_CREDENTIAL_DELETE`    | `SECRETS`        | Git credentials were deleted |
| `GIT_CONNECTION_POLICY`    | `SECURITY`       | The [Git connection policy](/administration/management/cluster-admin-settings/git-connection-policy) was checked when a user connected a project to a repository. The outcome shows whether the policy blocked the connection |
| `SECURITY_SETTINGS_CHANGE` | `SECURITY`       | A security setting changed, such as an OAuth app registration or the Git connection policy |
| `COPILOT_SETTINGS_CHANGE`  | `INFRASTRUCTURE` | AI model settings changed. The event records which settings changed, not their values |

## Execution plane events

Execution plane events record actions performed directly on the execution plane, the orchestrator service running in your environment. The execution plane sends these events to the control plane as they happen, and Prophecy stores them with the control plane events.

### Fabric

| Event type             | Category    | Description                          |
| ---------------------- | ----------- | ------------------------------------ |
| `FABRIC_CREATE`        | `DATA_FLOW` | A fabric was created                 |
| `FABRIC_CONFIG_UPDATE` | `DATA_FLOW` | A fabric's configuration was updated |
| `FABRIC_DELETE`        | `DATA_FLOW` | A fabric was deleted                 |

### Connections and secrets

| Event type             | Category    | Description                    |
| ---------------------- | ----------- | ------------------------------ |
| `CONNECTION_CREATE`    | `DATA_FLOW` | A connection was created       |
| `CONNECTION_UPDATE`    | `DATA_FLOW` | A connection was updated       |
| `CONNECTION_DELETE`    | `DATA_FLOW` | A connection was deleted       |
| `FABRIC_SECRET_CREATE` | `SECRETS`   | A secret was added to a fabric |
| `FABRIC_SECRET_UPDATE` | `SECRETS`   | A fabric secret was updated    |
| `FABRIC_SECRET_DELETE` | `SECRETS`   | A fabric secret was deleted    |

### Deployment and pipeline runs

| Event type                 | Category  | Description                                                                                                                     |
| -------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `PROJECT_DEPLOY`           | `COMPUTE` | A project was deployed to a fabric                                                                                              |
| `PIPELINE_RUN_INTERACTIVE` | `COMPUTE` | A pipeline was run interactively, for example from the Prophecy IDE                                                             |
| `PIPELINE_RUN_SCHEDULED`   | `COMPUTE` | A pipeline run was triggered by a schedule                                                                                      |
| `PIPELINE_RUN_SYNC_API`    | `COMPUTE` | A pipeline was run synchronously through the REST API                                                                           |
| `PIPELINE_RUN_TRIGGERED`   | `COMPUTE` | A pipeline run started. Recorded for every kind of run, with who or what started it                                             |
| `PIPELINE_RUN_CANCEL`      | `COMPUTE` | A request to stop a pipeline run was made in the UI or through the API, whether or not the run was stopped                      |
| `PIPELINE_RUN_CANCELLED`   | `COMPUTE` | A pipeline run ended because it was cancelled, with who or what cancelled it, such as a user or a schedule's concurrency policy |
| `PIPELINE_RUN_RESTART`     | `COMPUTE` | A user restarted a scheduled pipeline run                                                                                       |

### Schedules

| Event type        | Category  | Description                                                                      |
| ----------------- | --------- | -------------------------------------------------------------------------------- |
| `SCHEDULE_CREATE` | `COMPUTE` | A schedule was created                                                           |
| `SCHEDULE_UPDATE` | `COMPUTE` | A schedule was updated                                                           |
| `SCHEDULE_DELETE` | `COMPUTE` | A schedule was deleted                                                           |
| `SCHEDULE_PIN`    | `COMPUTE` | A pipeline's schedules were locked to a project version, or the lock was removed |

### DataBox uploads

| Event type                   | Category        | Description                                                                                                |
| ---------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------- |
| `DATABOX_UPLOAD_REMOVED`     | `DATA_PLATFORM` | A DataBox upload failed its background safety scan and was permanently deleted                             |
| `DATABOX_UPLOAD_SCAN_FAILED` | `DATA_PLATFORM` | A DataBox upload couldn't be scanned after repeated attempts and was kept without a scan                   |
| `DATABOX_UPLOAD_VANISHED`    | `DATA_PLATFORM` | A DataBox upload was moved or deleted outside DataBox, for example by a pipeline, before its scan finished |

## Sync data to S3

If your Prophecy deployment is hosted on AWS, you can sync your Prophecy audit logs to your own Amazon S3 bucket. Follow these steps to configure your S3 bucket and grant Prophecy the required access.

### 1. Create the S3 bucket

1. Open the Amazon S3 console and choose **Create bucket**.
1. Enter a **Bucket name**, following the format `prophecy-customer-audit-events-foo`. Replace `foo` with an identifier for your organization.
1. Choose a **Region**. Prophecy syncs to whichever region your bucket is created in — there's no region you need to avoid or request special handling for.
1. Set **Object Ownership** to **ACLs disabled (recommended)**. You can also apply this setting after creation by editing the bucket permissions.
1. Complete the remaining setup options as needed, then create the bucket.

### 2. Configure bucket permissions for Prophecy

1. In the Amazon S3 console, open your bucket and choose the **Permissions** tab.
1. Under Bucket policy, select **Edit**.
1. Paste the following policy JSON, replacing the placeholders as described below.

```json
{
  "Version": "2008-10-17",
  "Statement": [
    {
      "Sid": "DataSyncCreateS3LocationAndTaskAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::##############:role/AWSDataSyncS3BucketAccessCustomerAuditEventsRole"
      },
      "Action": [
        "s3:GetBucketLocation",
        "s3:ListBucket",
        "s3:ListBucketMultipartUploads",
        "s3:AbortMultipartUpload",
        "s3:GetObject",
        "s3:ListMultipartUploadParts",
        "s3:PutObject",
        "s3:GetObjectTagging",
        "s3:PutObjectTagging",
        "s3:DeleteObject"
      ],
      "Resource": [
        "arn:aws:s3:::prophecy-customer-audit-events-foo",
        "arn:aws:s3:::prophecy-customer-audit-events-foo/*"
      ]
    },
    {
      "Sid": "DataSyncCreateS3Location",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::##############:user/s3access"
      },
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::prophecy-customer-audit-events-foo"
    }
  ]
}
```

To use this example JSON:

- Replace all instances of `prophecy-customer-audit-events-foo` with your bucket name. Don't use the full bucket ARN, because the policy already includes the `arn:aws:s3:::` prefix.
- Replace `##############` with Prophecy's AWS account ID. Contact Prophecy to get the account ID.
- The two statements grant access for different purposes: the first lets Prophecy's sync role read your bucket's location and read/write objects at transfer time. The second — the `DataSyncCreateS3Location` statement — grants Prophecy's `s3access` IAM user the `s3:ListBucket` permission it needs to register your bucket as a sync destination in the first place. Both are required.

If your bucket uses a customer-managed KMS key, also grant the Prophecy sync role (`AWSDataSyncS3BucketAccessCustomerAuditEventsRole`) `kms:Encrypt`, `kms:GenerateDataKey*`, and `kms:DescribeKey` in your key policy. Without this, the sync will create successfully but fail when Prophecy tries to write objects.

### 3. Send Prophecy your bucket details

After applying the policy, contact Prophecy and provide:

- Your bucket ARN.
- The AWS region.

Prophecy will complete the configuration and enable syncing for your environment.
