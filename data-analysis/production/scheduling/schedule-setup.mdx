Use Prophecy's built-in scheduler to automate pipeline runs based on time or file triggers. You can create multiple schedules for a single pipeline, each with its own configuration including parameter sets, triggers, and alerts.

## Prerequisites

To leverage the built-in scheduler, your project must use the [Simple Git Storage Model](/data-analysis/development/versioning/git-storage-model). Prophecy's built-in scheduler does not appear in projects that use the Normal Git Storage Model.

## Configure a schedule

To configure a schedule for a pipeline:

1. Open a pipeline in the project editor.
1. Expand the **...** menu in the pipeline canvas header.
1. Click **Schedule**.
1. To create a new schedule, click **New schedule**. To edit an existing schedule, select it from the schedules list.
1. In **Choose Pipeline Parameter Set**, select a pipeline [parameter set](/data-analysis/development/parameters/parameter-sets) you want to use for this schedule.
1. Set a **Concurrency Policy** for the schedule: Skip, Queue, or Cancel. See [Set a concurrency policy](#set-a-concurrency-policy) below.
1. Under **Trigger**, configure the [trigger](/data-analysis/production/scheduling/triggers) for the schedule.
1. Under **Which version runs**, choose whether the schedule always uses the latest published version or locks to one specific version. See [Lock a schedule to a version](#lock-a-schedule-to-a-version) below.
1. Optionally, set up an [email alert](/data-analysis/production/scheduling/alerts) in your schedule. You can also choose to run data quality **Tests** as part of the schedule.
1. Click the switch next to the schedule name to enable the schedule.
1. Click **Save**.
1. In the confirmation dialog, click **Publish Now** to publish the project and activate the schedule, or click **Later** to publish another time.

For time-based schedules, the dialog summarizes the schedule and its time zone and shows when the next run occurs. If the project has unpublished changes, the summary notes that the schedule starts running after you publish the project. Click **Show the next 5 runs** to see upcoming run times.

You can create multiple schedules for the same pipeline, each with different parameter sets, triggers, and timing configurations. This allows you to run the same pipeline with different settings at different times or frequencies.

## Set a concurrency policy

The **Concurrency Policy** setting controls what happens when a scheduled run is due to start while the previous run of the same pipeline is still in progress. Concurrency policies apply only to time-based schedules, not to file arrival [triggers](/data-analysis/production/scheduling/triggers).

For example, suppose you schedule a pipeline to run every hour, on the hour. The 5:00 PM run is slow and doesn't finish until 6:30 PM, so the 6:00 PM run comes due while the 5:00 PM run is still in progress. The concurrency policy determines how Prophecy handles the 6:00 PM run:

| Policy | What happens to the 6:00 PM run | Result |
| :-- | :-- | :-- |
| **Queue** (default) | Waits, then starts as soon as the 5:00 PM run finishes at 6:30 PM. | Every run happens, but runs can drift off schedule. |
| **Skip** | Doesn't run. The next run starts at 7:00 PM as usual. | Runs stay on schedule, but some time slots are missed. |
| **Cancel** | Prophecy stops the 5:00 PM run so the 6:00 PM run can start. | The newest run always proceeds, and the older run is cut short. |

Schedules that don't have a concurrency policy set use **Queue**. **Queue** holds at most one waiting run. If a long run overlaps several time slots, Prophecy starts one late run when the long run finishes, not one run for each missed slot.

Consider **Skip** or **Cancel** when a pipeline can take longer to run than the interval between scheduled runs. For example, if a pipeline takes 20 minutes but is scheduled every 5 minutes, **Queue** causes each run to start as soon as the previous one ends, so the pipeline runs back to back indefinitely.

The policy you choose affects how runs appear in [Observability](/data-analysis/production/monitoring):

- **Cancel**: The stopped run appears with a **Cancelled** status rather than as a failure, and no failure [alert](/data-analysis/production/scheduling/alerts) is sent.
- **Skip**: A skipped time slot doesn't create a run record.

<Note>
If Prophecy can't cancel the in-progress run, the schedule falls back to **Queue** behavior for that run.
</Note>

## Lock a schedule to a version

By default, a schedule always runs whichever version of the project is currently published. That is, when the team publishes a new version, the schedule automatically moves to this version for the next run. You can instead _lock_ a schedule to one specific published version, so the scheduler keeps running that version no matter how many times the project is republished.

To change or remove a lock, open the schedule and update **Which version runs**:

- Select **Always the latest published** to unlock the schedule and have it follow future publishes again.
- Select **Lock to a specific version** and choose a different version to move the lock forward.

<Note>
A locked schedule that's already running a locked version is unaffected by publishing. Publishing makes no change to it until you update the lock yourself.
</Note>

<Note>
Locks apply per fabric. The same schedule can be locked to a version on one fabric's deployment while following the latest published version on another.
</Note>

## Activate schedules

Enabling a schedule does **not** automatically activate it. To activate your schedules, [publish the project](/data-analysis/production/publication). When you publish a project, Prophecy deploys all enabled schedules to your selected fabrics. In other words, your scheduled pipelines will begin running in the fabrics you selected.

Any time you make changes to a schedule (including enabling, disabling, or editing the configuration), you must republish the project for those changes to take effect.

## Delete a schedule

To delete a schedule:

1. Open a pipeline in the project editor.
1. Expand the **...** menu in the pipeline canvas header.
1. Click **Schedule**.
1. Select the schedule you want to delete.
1. Click the trash icon next to the schedule name.
1. Click **Delete schedule** to confirm the deletion.
1. Click **Save**.

When you delete a schedule, you still have to publish the project for the changes to take effect in the deployed pipeline.

## What's next

Once you have set up your schedules:

- Monitor automated pipeline runs in the [Observability](/data-analysis/production/monitoring) interface.
- Set up [email alerts](/data-analysis/production/scheduling/alerts) to stay informed about your scheduled pipeline runs.
- Learn more about different [trigger types](/data-analysis/production/scheduling/triggers).
