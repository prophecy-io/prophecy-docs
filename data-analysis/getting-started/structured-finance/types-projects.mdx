title: Types projects
description: Define your organization's shared business types, fields, and data checks, and publish them as versioned ontologies.

A Types project holds your organization's ontology: a shared set of business types, such as Loan, Deal, and Tranche, with typed fields and data checks. Other projects can use these types as harmonization targets. The Agent uses types to classify incoming tapes and map their columns.

You can build types by hand or have the Agent build them from a source document. When the ontology is ready, you publish it as a numbered version.

</Callout>

## Create a Types project

Only workspace admins can create a Types project. For other users, **Types project** is unavailable.

1. Open **Projects** in the left navigation.
1. Once in **Projects**, select **Create New → Types project**.
2. In **Create a Types Project**, enter a **Name**. Use only letters, numbers, and underscores (for example, `us_auto_abs`).
3. Optionally, enter a **Description** (for example, "Shared types for structured finance: Loan, Deal, Tranche.").
4. Click **Create Types Project**. The project opens in the Types editor.

A project name is required. If it's missing, the dialog shows "Name is required". If it contains characters other than letters, numbers, and underscores, Prophecy rejects the name.

To find Types projects later, open **Projects** and select the **Types** tab.

## Build types from a source document

You can have the Agent create types and fields from a source document. You can upload one file at a time. File types can be `xlsx`, `pdf`, `docx`, `yaml`, `json`, `csv`, `xml`, or `zip`, and files can be up to 4GB in size.

1. On the **Create a new Types Project** screen, click **Click to upload** or drag a file onto the page.
2. Click **Build Types Project**. The Agent reads the file, creates types and fields, and summarizes what it built in the chat. (This may take a few minutes.)
3. Review the proposed types. 
4. For each type, click **Accept all**, and then confirm in **Accept all suggestions on this type**.

## Add types manually

A type can be a root type or a child of another type. A child type can have only one parent. A new type requires both a name and a description.

1. To add a root type, click **+** next to **Types** in the tree. Enter a **Name** and **Description**, and then click **Create type**.
2. To add a child type, hover over a type in the tree and click its **+**. In **Extend \<type\>**, enter a **Name** and **Description**, and then click **Create type**.

A child type inherits all of its parent's fields. On the child type, these fields appear under **Inherited from \<parent\>** and are read-only, with the message "Inherited fields are read-only. Open the parent type to edit them." Fields declared on the child appear under **Declared on \<type\>**.

## Add and edit fields
Fields are the typed attributes of a type. Each field has a name and a data type, and a description and data checks.
 
Fields you add to a type are inherited by all of its child types.
1. Select a type, and then click **Add field**.
2. In **New Field**, enter a **Name**, choose a **Type**, and enter a **Description**. Available types are String, Integer, Decimal, Float, Boolean, Date, Time, DateTime, and DateTimeTz.
3. Click **Create Field**.
4. To edit a field, click its row in the fields table. The field panel opens on the right.

Field names must be unique within a type, including inherited fields. A duplicate name shows "This type already has a field called \<name\>".

The field panel shows which type declares the field and how many types inherit it. In addition to the name, type, description, and checks, the panel includes:

- **Policies → Skip mapping**, which stops Prophecy from mapping or updating the field. Use it for values entered by hand or values that should stay unchanged.
- **Memories**, which are notes the Agent keeps about the field.

An empty description appears as `-`.

## Add checks to a field

A check is a SQL expression that is true for every valid row. Checks run during harmonization. Checks on a parent field also apply to every child type.

1. In the field panel, under **Checks**, click **Add check**.
2. Enter a SQL expression (for example, `current_balance >= 0`), and then click **Save**.
3. To have the Agent write the check, click **Use AI to write this check**. In **Write a check with AI**, describe the check (for example, "every value is between 1 and 6, and never null") and click **Save Prompt**.
4. To change or remove a check, hover over it and click the pencil icon. Then edit the check, click **Remove**, or use the AI icon to rewrite it.

A check written with AI is sent to the Agent as a chat message that includes the instruction and a `Type.field` label.

Check expressions aren't validated when you save them, so a typo in a check isn't flagged.

## Work with the Agent

When you select a type or field, it's added to the chat input as a chip (for example, `Loan` or `current_balance`) and sent to the Agent as context.

Types, fields, and checks the Agent creates are suggestions. They appear highlighted in green as proposed changes and stay pending until you accept them. Accept them with **Accept all** on the type or field, or one at a time with the check and cross icons.

Use the mode menu in the header to control how your own edits are applied:

| Mode | Behavior |
| --- | --- |
| **Editing** | Your edits change the draft. |
| **Suggesting** | Your edits become suggestions. |

The **Decisions** tab lists pending **Suggestions** and saved **Memories** for review.

## View the ontology source

To see the underlying `ontology.yml`, click the **⋮** menu on a type and select **Code view**. Click **Back to fields** to return.

You can't edit `ontology.yml` directly. Make changes to types, fields, and checks in the Types editor.

## Publish a version

Publishing creates a tagged version of the ontology.

1. Click **Publish**. The **Publish** panel lists **Changes to publish**, grouped by type. Click a type's change count to see each change.
2. Review **Version details**. The version number and description are filled in automatically. To change them, click **Edit**, and then click **Save**.
3. Click **Publish**.

After a publish, the next version number is suggested automatically (for example, v1 → v2), and the release note is drafted from your changes.

If you remove a field in a new version, existing mappings and hints for that field are kept.

**Publish** is disabled in the following cases:

| Condition | Tooltip |
| --- | --- |
| Agent suggestions are still pending | Resolve pending suggestions to publish |
| No type changes since the last version | Nothing to publish: no type changes since the last version |
| Version description is missing | Finish editing the version description first |
| Version number is missing or invalid | Please enter a valid version number |
| Compilation errors in the ontology | Resolve errors to publish |

## Manage the project

Click the **⋯** menu next to the project name to open **Version History**, **Duplicate Project**, **Rename Project**, and **Delete Project**. Select **Version History** to see the project's published versions.

To roll back to an earlier version, select **Version History**, and then select the version you want to return to. **Version History** lists all of the project's published versions.

When you duplicate a Types project, the copy keeps everything from the original except prompts entered in the Agent chat.

Clicking the project name in the header keeps you in the Types editor.
