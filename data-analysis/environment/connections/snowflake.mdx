A Snowflake connection lets Prophecy read from and write to tables in your Snowflake account. Use it with Source and Target gems, browse tables in the Environment browser, and process Snowflake data in Prophecy pipelines.

This page covers Snowflake connections used to access data. To use Snowflake as the compute engine for a fabric, see [Create a Snowflake fabric](/data-analysis/environment/fabrics/create-fabrics/snowflake).

## Connection types

You can use Snowflake in two ways in Prophecy.

| Connection type               | Description                                                  |
| ----------------------------- | ------------------------------------------------------------ |
| **SQL Warehouse connection**  | Snowflake acts as the compute engine for a fabric and executes pipeline SQL transformations. To learn more about SQL Warehouse connections, see [Prophecy fabrics](/data-analysis/environment/fabrics/prophecy-fabrics). |
| **Ingress/Egress connection** | Snowflake is used only as a data source or target. Pipelines read from or write to Snowflake tables while transformations run in another warehouse. |

## Feature support

The following table shows which Prophecy features each connection type supports.

| Feature                            | SQL Warehouse | Ingress/Egress |
| ---------------------------------- | ------------- | -------------- |
| Run SQL queries                    | Yes           | No             |
| Read data with Source gem          | Yes           | Yes            |
| Write data with Target gem         | Yes           | Yes            |
| Browse data in Environment browser | Yes           | Yes            |
| Index tables in Knowledge Graph    | No            | No             |

## Prerequisites

Prophecy runs all data operations, such as reads and writes, with the Snowflake credentials you provide in the connection. Grant your Snowflake user or role the privileges for the operations your pipelines perform.

| Operation                 | Required privileges |
| ------------------------- | ------------------- |
| Connect and run queries   | `USAGE` on the warehouse, database, and schema |
| Read data                 | `SELECT` on the tables used in your pipelines |
| Write data                | `INSERT`, `UPDATE`, and `DELETE` on the tables used in your pipelines<br />`CREATE FILE FORMAT` in the target schema<br />`USAGE` on any file formats used for reading or writing Parquet files<br />Write access to your user stage |
| Alter or replace tables   | `OWNERSHIP` on the table |

When you write data through a Snowflake connection, Prophecy uploads Parquet files to your user stage and then loads them into Snowflake tables. This is why write operations require file format and stage access.

## Connection parameters

<Warning>
Starting October 2026, Snowflake enforces the deprecation of password-based sign-in for service users. Connections that authenticate with a username and password stop working once Snowflake enforces the cutover. Prophecy flags affected connections with a **Password auth** badge on the **Connections** tab. Move these connections to [key-pair or OAuth authentication](/data-analysis/environment/fabrics/create-fabrics/snowflake).
</Warning>

To create a connection with Snowflake, enter the following parameters:

| Parameter             | Description |
| --------------------- | ----------- |
| Connection Name       | Name to identify your connection |
| Account               | URL for your Snowflake account<br />Example: `https://<orgname>-<account_name>.snowflakecomputing.com` |
| Database              | Default database for reading and writing data |
| Schema                | Default schema for reading and writing data |
| Warehouse             | Name of the Snowflake virtual warehouse used to execute queries for this connection |
| Role                  | Snowflake [role](https://docs.snowflake.com/en/user-guide/security-access-control-overview) used for the connection. Use a role with only the privileges listed in [Prerequisites](#prerequisites).<br />Example: `PROPHECY_ROLE` |
| Authentication method | Use key-pair or OAuth authentication. To configure key-pair authentication, see [Key-pair authentication](#key-pair-authentication). To configure OAuth, see [Create a Snowflake fabric](/data-analysis/environment/fabrics/create-fabrics/snowflake#oauth). OAuth requires a Snowflake app registration that a cluster admin creates. See [OAuth app registrations](/administration/management/cluster-admin-settings/oauth-setup).<br />Password authentication is deprecated. If you still use it, enter your Snowflake username and use a [secret](/data-analysis/environment/secrets/secrets) to enter your password. |

### Key-pair authentication

Key-pair authentication signs in to Snowflake with an RSA private key that you store in a Prophecy [secret](/data-analysis/environment/secrets/secrets). Before you begin, [assign the public key](https://docs.snowflake.com/en/user-guide/key-pair-auth) to the Snowflake user that the connection uses.

The private key must be an unencrypted PKCS#8 key. The first line of the key file must be `-----BEGIN PRIVATE KEY-----`. If your key is encrypted (`-----BEGIN ENCRYPTED PRIVATE KEY-----`) or in PKCS#1 format (`-----BEGIN RSA PRIVATE KEY-----`), convert it with OpenSSL:

```bash
openssl pkey -in rsa_key.p8 -out rsa_key_unencrypted.p8
```

To configure key-pair authentication:

1. In the fabric, create a **Text** secret. Click **Or Upload File** and upload the private key file.

   Upload the file instead of pasting the key into **Value**. Pasting can remove the line breaks the key requires.

1. In the connection, under **Authentication method**, select **Key Pair**.
1. Enter the **Username** of the Snowflake user that has the public key assigned.
1. For **Private Key**, select the secret you created.
1. Leave **Private Key Passphrase (Optional)** empty.

<Note>
Key-pair authentication doesn't support passphrase-protected private keys. Use an unencrypted private key.
</Note>

<Warning>
Anyone with the unencrypted key file can sign in as its Snowflake user. After you upload the key to the secret, delete the local file or store it securely.
</Warning>

## Limitations

Snowflake connections have the following data type limitations:

- Prophecy reads `OBJECT`, `ARRAY`, and `VARIANT` columns as `STRING`.
- Prophecy does not support writing `BINARY` columns.
- On Databricks and BigQuery, Prophecy maps `DECIMAL` and `NUMERIC` to floating-point types, which can reduce precision. Avoid this conversion for values that require exact precision, such as currency.
- On Databricks and BigQuery, Prophecy maps `NUMBER` to an integer type, so values with a decimal scale lose their fractional digits.
- On Databricks, Prophecy maps `TIME` to `STRING`.

## Sharing connections within teams

Prophecy stores connections in [fabrics](/data-analysis/environment/fabrics/prophecy-fabrics), which are assigned to specific teams. When you add a Snowflake connection to a fabric, every team member with access to that fabric can use the connection in their projects. Team members don't authenticate separately. They inherit the access and permissions of the stored connection credentials.

How sharing works for connections that use OAuth authentication: Not specified in source material.

<Warning>
Anyone on the team has the same permissions as the stored credentials, including access to sensitive data if those credentials allow it.

To limit access to high-sensitivity connections, create a dedicated fabric and team for them so only approved users can use those credentials.
</Warning>
