A Snowflake fabric uses a Snowflake virtual warehouse as the compute engine for your pipelines. Prophecy runs pipeline SQL in the warehouse and reads and writes tables in the database and schema you configure.

To use Snowflake only as a data source or target, create a Snowflake [connection](/data-analysis/environment/connections/connections) instead.

<Callout icon="/images/icon.png" color="#FFC107">

Available for [Express and Enterprise Editions](/data-engineering/administration/platform/editions) only.

</Callout>

## Prerequisites

Before you create a Snowflake fabric, make sure you have:

- A Snowflake account URL.
- A Snowflake warehouse to execute queries.
- A role with permissions to use the warehouse, access the database and schema, and read and write to the stage Prophecy uses for temporary files.
- Credentials for your authentication method: for key-pair authentication, a key pair whose public key is assigned to your Snowflake user; for OAuth, an app registration configured by your cluster admin.

## Create a Snowflake fabric

<Note>
You can't change the fabric provider after you create the fabric.
</Note>

<Steps>
<Step title="Create a new fabric entity">

1. From the left sidebar, click the **+** sign.
1. On the Create Entity page, select **Fabric**.

</Step>

<Step title="Fill in the Basic Info tab">

The **Basic Info** tab defines the key identifiers of the fabric.

1. Provide a name for the fabric.
1. (Optional) Provide a description for the fabric.
1. Select a [team](/data-analysis/administration/management/teams/teams) that can access the fabric.
1. Click **Continue**.

</Step>

<Step title="Fill in the Providers tab">

The **Providers** tab configures the SQL warehouse provider for the fabric.

1. Under **Provider**, select **Snowflake**.

1. Enter your **Account URL**.

   Example: `https://uuywwsi-xxxxxxxx.snowflakecomputing.com`

1. Enter the **Role** that Prophecy uses to access Snowflake resources.

   Example: `TRANSFORM_ROLE`

1. Enter the **Warehouse** that executes the SQL queries your pipelines generate.

   Example: `ANALYTICS_WH`

1. Enter the default **Database** where Prophecy reads and writes data.

   Example: `ANALYTICS`

1. Enter the default **Schema** where Prophecy reads and writes data.

   Example: `PIPELINES`

1. Enter the **Prophecy Dataplane URL**, which Prophecy uses to orchestrate pipeline execution and data movement.

1. Select an authentication method and enter its credentials. For the fields each method requires, see [Authentication methods](#authentication-methods).

1. Provide the **Stage** where Prophecy stores temporary files during pipeline orchestration. The configured role must have read and write permissions on the stage.

   Example: `@PROPHECY_STAGE`

</Step>

<Step title="Save the fabric">

Click **Complete** to save the fabric.

</Step>
</Steps>

<Note>
After you save the fabric, you can add [secrets](/data-analysis/environment/secrets/secrets) and [connections](/data-analysis/environment/connections/connections) to it.
</Note>

## Authentication methods

Snowflake fabrics support the following authentication methods.

### Key-pair

Key-pair authentication uses an RSA key pair instead of a password.

1. Enter the **Username**.
1. Upload your **Private Key** file.

The private key must be an unencrypted PKCS#8 key. The first line of the key file must be `-----BEGIN PRIVATE KEY-----`. If your key is encrypted (`-----BEGIN ENCRYPTED PRIVATE KEY-----`) or in PKCS#1 format (`-----BEGIN RSA PRIVATE KEY-----`), convert it with OpenSSL:

```bash
openssl pkey -in rsa_key.p8 -out rsa_key_unencrypted.p8
```

<Note>
Key-pair authentication doesn't support passphrase-protected private keys. Use an unencrypted private key or a different authentication method.
</Note>

### OAuth

Use OAuth when an identity provider or service principal manages authentication.

Select an **App Registration** from the dropdown. The dropdown lists the OAuth app registrations your cluster admin has configured for Snowflake, including native **Snowflake** registrations and any **ID Anywhere (Snowflake)** registrations. ID Anywhere registrations authenticate through an ADFS or ID Anywhere identity provider instead of Snowflake's native OAuth. If the registration you need isn't listed, ask your cluster admin to add it under **Settings** > **Admin** > **Security**. To learn how to create app registrations, see [OAuth app registrations](/administration/management/cluster-admin-settings/oauth-setup).

If sign-in through an ID Anywhere (Snowflake) registration fails with a claim mismatch error, the claim that carries the Snowflake username in the ADFS access token doesn't match Snowflake's `EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM`. Ask your cluster admin to check the [ID Anywhere (Snowflake) setup](/administration/management/cluster-admin-settings/oauth-setup#id-anywhere-snowflake).

## Migrate from password authentication

<Warning>
Snowflake is deprecating password-based sign-in for service users as of October 2026. New fabrics don't offer **Username and Password**. This option appears only on existing fabrics that already use it, and those fabrics stop connecting once Snowflake enforces the cutover. To switch to a supported method, see [Migrate from password authentication](#migrate-from-password-authentication).
</Warning>

Prophecy shows a banner and a **Migrate** action on fabrics that still use **Username and Password** authentication. To move an affected fabric to **Key-pair** or **OAuth** authentication, click **Migrate** on the fabric.

## Limitations

Snowflake fabrics don't support:

- Case-sensitive identifiers.
- Creating new partitioned tables.
- Modifying partitioning of existing tables.
