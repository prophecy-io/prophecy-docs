Skills tell Prophecy's AI agent how to handle a specific task: when to activate, what to read first, how to proceed, and what to hand off when done. This page covers how to structure a skill file and what to expect as you iterate on it.

<Note>
Skills are an iterative artifact. The structure described here reflects patterns that work well in practice, but there is no single correct form. Expect to revise a skill as you learn how the agent interprets it and how users actually phrase their requests.
</Note>

## What a skill file is

A skill is a folder containing a `SKILL.md` file and any supporting reference files. Skills conform to the [Agent Skills open specification](https://agentskills.io/specification), which defines a portable, interoperable format for agent instructions.

In Prophecy, skills live at `skills/<skill-name>/SKILL.md` in your project.

## How the agent loads skills

The agent reads the **name and description** of every installed skill on every chat. It only loads the full skill body when it determines the skill is relevant to the current task. This means:

- You can maintain many skills without degrading agent output
- The description is doing active routing work, not just documentation
- A vague description means the skill may never load — or may load at the wrong time

## Frontmatter

The frontmatter contains two required fields:

```yaml
---
name: your-skill-name
description: >
  Use when the user wants to [do X]. Triggers include:
  "[phrase 1]", "[phrase 2]", or when the user uploads a [file type]
  that appears to be [description].
---
```

| Field             | Description                                                  |
| ----------------- | ------------------------------------------------------------ |
| **`name`**        | This is a slug that becomes the folder name. Use lowercase letters, numbers, and hyphens only. |
| **`description`** | This is the routing signal the agent uses to decide when to load this skill.  Start with "Use when..." and be as concrete as possible. <br/><br/>Include: <br/>- The user intent it targets <br/>- Specific trigger phrases (quoted) <br/>- File types or contextual signals that should activate it - Where relevant, what the skill does *not* cover |

A vague description like "Helps with data mapping" gives the agent little to work with. A scoped one like `Use when the user wants to map a raw data tape to the CDM. Triggers include: 'crack this tape', 'map to CDM', 'harmonize tape'` tells it exactly when to act.

## Skill body

The body has no required schema, but it helps to decide up front what kind of content you're writing:

- **Reference content** — knowledge the agent applies passively. Conventions, domain terminology, design principles. Loads when relevant and stays in context.
- **Task content** — step-by-step instructions for a specific action. Deployments, checklists, multi-step procedures. Often better invoked directly than triggered automatically.

The following sections appear consistently in well-formed skills.

<Note>
Skill body content stays in context for the entire session once loaded. Keep it concise: every line is a recurring token cost. Move large reference material to supporting files in the same skill directory and link to them from `SKILL.md`.
</Note>

### Opening context line

A one-line summary of what stage or role this skill plays:

```
Runtime Stage 1 skill. Thin wrapper around Prophecy's built-in Harmonization Agent.
```

This helps orient anyone reading the file and helps the agent understand its own scope.

### `<important_rule>`

An XML-tagged block that fires as the agent's first instruction. Use it for things that must happen before any other step:

```xml
<important_rule>Before executing, create a task plan: (1) Confirm the asset class — ASK if ambiguous, (2) Read the correct knowledge base, (3) Proceed with harmonization.</important_rule>
```
Keep this concise. It runs every time the skill activates.

### Before you start

Pre-conditions and required reading before the agent acts. Typically: which knowledge base or config files to load, and any branching the agent needs to resolve first.

### What you do

The ordered happy-path steps. Number them. Use `—` to separate the action from the reason:

```markdown
1. **Identify CDM** — determine which config to use based on asset class
2. **Trigger harmonization** — point the agent at the correct CDM
3. **Monitor output** — expect 80–90% auto-match; LLM handles the remainder
```

Be specific where the agent needs precision. Be general where the product handles the details.

### What you do NOT do

Explicit guardrails. This section prevents the agent from going off-script in predictable ways:

```markdown
- Do NOT write custom mapping logic — the product handles this
- Do NOT modify the CDM at runtime — that's a design-time operation
```

### After [task] completes

What the agent should suggest or do next. Include handoff language and any routing to a follow-on skill:

```markdown
Suggest generating a Silver data profile:
"[Task] is complete. Would you like me to generate a Silver data profile?"

Route to `skill-name/silver-profile` if the user agrees.
```

### Key gotchas

Edge cases and issuer-specific exceptions the agent should flag when relevant. Start minimal and add from real usage.

## Uploading a skill

Once your file is ready, upload the skill to Agent and give it the following prompt:

```
Upload this skill to skills/<name>/SKILL.md and sync the project.
```

The agent will:
1. Read the file from the attachment
2. Parse the `name:` field to determine the folder
3. Write the file to `skills/<name>/SKILL.md`
4. Call `update_files` to sync it to your project browser
